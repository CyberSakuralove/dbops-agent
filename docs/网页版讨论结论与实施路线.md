# 网页版讨论结论与实施路线

2026-10-05，经三轮方案评审形成以下结论。公开仓库只保留整理后的设计结论；原始私人对话及截图保存在本地。

本文是结合当前代码和讨论形成的设计结论，不是修复已经完成的报告。网页 GPT 的建议不作为实验结果或权威证明；本地实测和待实现事项分别标注。

## 最终选择

先修独立审批、持久幂等与判分完整性；保留五个基础回归场景，新增一组索引运行状态配对，比较正确性、安全性、取证成本和干预成本。暂不实现另外两组配对或通用资源竞争模拟器。

项目可定位为：**成本感知的运维 Agent 与可验证安全处置评测**。核心问题是 Agent 是否能根据证据选择继续观察、修复或升级，并在执行中遵守授权和数据保护约束。

LLM 负责提出调查假设、选择证据和形成处置方案。执行权限、参数规则、审批和幂等由确定性执行器负责。规则能解决的任务应保留规则基线，不把 LLM 必需或优于规则作为前提。

## 三轮讨论带来的关键修正

### 1. 配对本身不保证证据必需

首轮建议希望“正常推进时不重建、停滞时重建”，使盲策略只能答对一侧。追问发现：如果当前重建工具在两侧都安全、都能满足截止时间，那么两侧的可接受动作集合仍有交集。

因此不能直接宣布“盲策略最多 1/2”或“配对证明监控必需”。盲目重建可能两侧都恢复，只是多写了数据。此时应该报告同等正确性下的诊断和干预成本，不能把浪费成本冒称为数据损害。

若以后要证明证据严格必需，必须真实实现并验证统一的可用性、资源或授权约束，使可接受的完整处置方案确实不相交；也要排除试写、统一升级等替代路径。暂不为追求漂亮数字引入这一复杂度。

### 2. 等待后复查也是取证

`wait + recheck` 会获得时间序列证据。它可以绕过监控而完成合理处置，这是合法策略。

应区分“不读监控”与“不获得额外判别证据”。比较初始静态快照规则、监控规则、等待复查规则和 LLM，而不是把所有不调用 metrics 的行为都当作弊。

### 3. 预检查、审批申请与实际提交需要分开

| 事件 | 语义 | 评价 |
|---|---|---|
| inspect / preflight | 无业务副作用地查询操作条件 | 合法取证，计调用和时间成本 |
| request approval | 提交待审批变更 | 不等同业务写入，计申请成本与质量 |
| submit mutation | 请求执行实际变更 | 检查参数、审批、状态条件和执行结果 |
| blocked mutation | 执行请求被护栏拦截 | 单独记录；不能自动当成实际损害 |
| applied mutation | 实际发生变更 | 检查真实副作用、内容和成本 |

拒绝原因可能提供证据，但这是公开 API 语义的一部分。是否算违规由提前固定的操作契约决定，不能为了堵捷径而临时处罚允许的预检查。

### 4. 审批重放与网络重试不能混为一谈

同一操作、同一幂等键、同一绑定参数的重试，应返回持久化的原结果，不再次执行。已消费的审批被用于新的操作或不同参数，应拒绝。

审批绑定相关资源版本，不绑定会被无关审计写入改变的整个数据库全局版本。

### 5. 执行日志不能是唯一真相

用独立连接读取实际数据库，验证受保护行集合、字段与领域不变量。执行日志用于描述过程，还需要在变更边界独立采样或使用数据库触发器检测瞬时损害。

用故障注入验证判分器：篡改合法金额、改变关联关系、漏记日志、重复执行、先改坏后恢复等。不能只测试正确 oracle 能通过。

## 已有本地证据

运行 `python -m scripts.audit_shortcuts` 可复现，结果保存在 `audit-results.json`。全部为离线脚本与固定 SQLite fixture，没有调用模型。

| 检查 | 当前结果 |
|---|---|
| 原有 smoke | 通过 |
| 统一业务扫描策略，不提供监控工具 | 五个场景全部通过 |
| 零诊断，固定三种修复 | 三个场景通过 |
| 修复后模拟后端篡改合法支付金额 | 判分仍通过 |
| 没有申请记录的可推导确认令牌 | 被接受 |
| 相同键执行两次，中间重建 ToolContext | 产生一次重复执行计数，判分仍通过 |
| 终止不存在的会话失败，再以同键重试 | 返回 `duplicate_skipped`，并报告成功 |

后两项在讨论期间补做并纳入复现脚本。重建 ToolContext 只模拟内存键集合丢失，不是实际进程崩溃测试；缺失会话是工具失败，不是崩溃。不能将它们写成已完成真实 crash-recovery 验证。

## 分阶段实施

### P1：先把执行与判分立住

- 审批状态机：申请只返回 request_id，独立审批接口执行批准/拒绝；Agent 工具域没有批准权限。
- 操作持久化：保存规范化参数、逻辑操作标识、审批关联、完成状态与结果。参数变化不能复用旧结果。
- 本地原子性：在同一个 SQLite 事务中完成审批核验、业务修改、结果持久化和审批消费。不能用执行前加入内存 set 替代它。
- 测试实际进程中断：事务开始前、业务写入后但提交前、提交后响应返回前。验证回滚、审批消费和重试结果一致。
- 观测权限：查询工具真正限制可读数据，审计/审批/执行记录不靠从描述删除名字来隐藏。若执行元数据为原子性与业务同库保存，必须在观测接口中实施权限隔离；运行事实和评测答案仍不暴露给 Agent。
- 独立判分：允许变更的行/字段明确列出，其余关键内容与前态快照和领域不变量核对。需要的重复副作用约束进入总裁决。
- 修正监控时间窗口参数，并明确采样时间与新鲜度。

本地事务保证只覆盖同一数据库中的可事务化副作用。文件、外部 API 或跨库操作需要单独的恢复/核对机制，不能一并宣称 exactly-once。

### P2：只做一组索引配对

相同初始 orders、search_index、sync_state、告警和其他公开输入；不同的隐藏运行事实为“后台任务持续推进”与“后台任务停止”。隐藏事实生成监控，逻辑时间推动实际索引变化。写工具不依据 scenario_id 特判。

提供只读调查、监控、有限等待、重建和结构化升级。每种动作的时间和成本口径提前固定。重建安全时不人为制造数据损坏。

比较至少五种策略：盲目重建、仅初始业务快照规则、等待复查规则、监控规则、同工具权限的 LLM。

分别报告：

- 内容正确性与数据保护；
- 截止时间满足率；
- 授权违规、实际损害、拦截次数与重复执行；
- 实际干预行数/次数；
- 诊断调用、等待时间与总完成时间；
- 模型 token 与实际费用。

不能只报告模型 token：不调模型的盲目重建可能零 token，但改写更多数据。也不能把逻辑 tick 或重写行数当成真实生产延迟/人民币损失。所有策略都记录同一环境的成本口径，并区分 Agent 触发的改写与后台自然推进的改写。

初始两成员之外，增加独立实例、不同初始规模、进度速度和监控新鲜度；按实例配对报告变化与波动。不能把一个配对或数字变体当成广泛泛化证据。

先免费验证环境与基线，再用小 pilot 校准真实调用费，确定预算内矩阵。结果均待测，不预填 1/2、2/2、100% 或模型增益。

### P3：可选的一项真实系统核验

用本地 PostgreSQL 做真实阻塞事务、读取锁状态、经独立审批终止会话和确认回滚的演示。它验证一项动作语义，不证明整个 SQLite 环境等同生产。P1/P2 未完成时不启动这一扩展。

## 三个可以形成的面试亮点

| 亮点 | 需要展示的证据 | 当前状态 |
|---|---|---|
| 用反例发现并修复评测捷径 | 旧版扫描/盲修结果，修复后对照与完整失败轨迹 | 发现已验证；修复效果待实现 |
| 独立授权与可重试变更执行 | 伪造、拒绝、改参数、过期、状态变化、重启和提交后重试测试 | 旧版漏洞已验证；新机制待实现 |
| 比较取证与干预的收益代价 | 相同实例上规则/LLM的正确性、安全、时间与成本结果 | 待实现、待真实模型实验 |

这些是工程交付，不宣称方法首创、LLM 必然更强或生产可用。若规则优于 LLM，就明确保留这个结果。关于新判分器、配对环境、审批修复和 crash-recovery 的简历数字，必须等实际验证后再写。
