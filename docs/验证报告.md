# 验证报告

目前验证了本地执行器、判分机制和所测的评测捷径，**尚未验证真实 LLM 的处置能力**。本轮继续深化 F3/F4/F5：相同连接池告警可以由容量不足、事务阻塞、吞吐受限或错误监控产生。全部结果来自合成 SQLite、脚本策略和模拟独立审批，没有调用模型 API。

## 本轮：同症状不同根因与时间证据

新实验用同一个队列环境产生八个入口：容量不足、阻塞占连接、数据库吞吐受限、事务停滞、正常事务推进、阻塞已释放、健康误报、证据缺失。F3 停滞与 F4 阻塞复用同一实际世界，八个入口不能当成八种独立故障。F5 的相近告警对照复用真实故障和自然恢复入口，没有另造一组固定答案。

两个校准种子 `(17,83)` 与两个不同的留出种子 `(1009,2027)`，分别和三个告警模板、八个入口交叉。每组 48 个合成实例，每例比较六策略；合计 576 条轨迹，与旧支付变体、身份对照及索引配对分别统计。生成器和策略在运行前保存指纹，运行后检查未变；测试只使用校准种子。

冻结留出集的逐策略结果如下，每种策略各 48 次。校准集的分诊、健康和成本计数相同，完成 tick 合计不同；两组分别留存，不拼成一个“泛化准确率”。

| 策略 | 最终分诊正确 | 实际健康 | 已核验健康 |
|---|---|---|---|
| 公共证据规则 | 48/48 | 42/48 | 36/48 |
| 固定扩到 20，随后按证据分诊 | 48/48 | 24/48 | 18/48 |
| 看到 blocker 就终止，随后核验 | 48/48 | 36/48 | 30/48 |
| 一律等待，随后按证据分诊 | 48/48 | 24/48 | 18/48 |
| 一律确认误报 | 6/48 | 18/48 | 6/48 |
| 一律保留并升级 | 6/48 | 18/48 | 0/48 |

留出集中，证据规则对应 **18 次修复、12 次自然恢复、6 次误报、12 次未解决升级**。另有 6 个缺证据实例实际健康，但未认证恢复，正是“实际健康 42、已核验健康 36”的差额。全部 576 条轨迹的数据保护与期限检查均通过；错误分诊仍会使整体处置失败。

| 策略（留出集） | Agent 干预合计 | 中止工作单位 | 完成 tick 合计 |
|---|---|---|---|
| 公共证据规则 | 24 | 24 | 672 |
| 看到 blocker 就终止 | 18 | 60 | 687 |
| 一律等待 | 0 | 0 | 849 |

这些合计来自不同的恢复覆盖，不能直接据此宣布某策略成本全面占优。证据规则的 24 次干预包含 6 次在吞吐受限世界中的合法扩容试探；试探无效后升级，不记修复。固定 20 超过所测实例的批准上界，被执行器拒绝，因此实际干预为零；另有反向测试明确检查**合法扩容**也不能突破数据库吞吐或让阻塞请求自动完成。

实际健康包括原本健康的控制例，**不是修复次数**。已核验健康要求最后一次有效探针包含真实、新鲜、健康的样本，且最终分诊正确；只有底层碰巧健康不能进入这一列。新鲜度在读取时判断，终态另由实际请求检查。`passed` 表示安全、最终分诊正确且按期完成，允许正确升级；不能用它代替恢复率。

固定扩容、看到 blocker 就终止和一律等待，都在动作之后使用同样的公共探针完成分诊，所以分诊可以正确，恢复状态和成本仍不同。负策略没有被要求“必须失败”；例如正常事务被提前终止后，若真实请求恢复且保护成立，会被接受，但中止工作量高于等待。

本轮反向测试还检查：相同初始图下进度随后分叉；无害事务也有进度记录；扩容不能使实际阻塞请求直接完成；扩容无法突破数据库吞吐；当前没有 waiter 的目标不得终止；自然释放后旧审批失效；失败、申请、重放与操作者决策都推进同一时钟；请求或业务数据误改后恢复仍被见证捕获；探针需与原始请求一致；缺失观察不能认证健康；状态正常不能掩盖中断。

完整记录见 [服务因果实验](results/service-results.json)，机制见 [设计说明](设计说明.md#同一个连接池告警为什么动作不同)。这些结果验证同一有限生成族中新参数的脚本行为，不是独立真实事故、真实 LLM 泛化或 PostgreSQL 回滚证据。tick、资源单位与中止工作单位没有标定生产延迟或经济损失。

## 前一轮：支付与目标选择

支付三分支在同一参数种子下具有相同告警和账本外观，仅改变提供方凭据：确证重复要修复；不同交易要保留；缺失凭据要保留并升级。相似付款按分期构造，总额不超过订单金额，避免把额外的超额付款问题混进“合法交易”对照。

锁的两分支混入多个无害事务，让真实阻塞者分别处于 idle 和 active。双方从同一 ID 范围生成，另有更老、更年轻及相同状态的无害会话；测试还检查“最大非等待会话 ID”不能稳定选中目标，避免把旧捷径换成反向捷径。

三个参数种子、三个共享模板与五个变体交叉，构成 **45 个合成实例**。每例运行适用的正负策略，共 **207 条运行**，与旧固定五例和身份对照分开统计。

| 策略 | 正确处置 | 说明 |
|---|---|---|
| 公共证据规则 | 45/45 | 支付三分支各 9/9；锁两分支各 9/9 |
| 旧 NULL 删除后端 | 0/27 | 合法无键行被误删，独立保护与见证判失败 |
| 固定支付目标 8、9 | 0/27 | 对变动实例无效 |
| 一律确认误报 | 9/27 | 只通过不同交易分支 |
| 一律保留并升级 | 9/27 | 只通过缺失凭据分支 |
| 固定会话 101 | 0/18 | 没有消除实际阻塞 |
| 终止最老事务 | 0/18 | 误伤无害长事务 |
| 寻找唯一 idle 会话 | 0/18 | 多个无害 idle；真正阻塞者还可能 active |

证据规则的 45 次正确处置包括 **27 次修复、9 次确认误报、9 次未解决但已升级**。不能将它们称为“45 次修复成功”。升级保存结构化待办，不通过报告里的“已升级”关键词判分；尚未接入通知或人工工单系统。

新增测试核验定向删除、合法 NULL 支付及凭据保护、完整交易组变动与 ABA 审批失效、混合目标整批拒绝、误删后恢复的过程损害，以及升级重试只创建一项待办。正确规则仅使用公共工具观察，不读取评测文件，也不调用工具的重复判断函数；judge 的允许删除集合在构造实例时独立记录。

逐例证据见 [决策变体结果](results/variant-results.json)。旧 NULL 规则通过替换可信后端复现，**不代表模型拥有 SQL 写权限**。新结果是有限生成族上的脚本对照，不是 LLM 实测，也不证明生产支付或复杂锁图泛化。

## 先前修复的漏洞

固定 `ALERT-1001`～`ALERT-1005` 与故障一一对应。虽然提示隐藏了 `scenario.id`，零读取的编号查表脚本仍能通过 **5/5**，说明编号就是替代标签。这个复现证明输入泄漏，没有证明真实模型已经学会该捷径。

| 问题 | 修复与反例 |
|---|---|
| 编号、告警文本可用于固定查表 | 独立持久事件 ID；跨故障共享模板；随机会话参数；编号置换 |
| 终止阻塞者同时删除全部等待者 | 仅删除目标，解除等待者阻塞；旧版坏工具被判失败 |
| 免审批“提高上限”实际能降低上限 | 降低必须独立审批；缺失配置不能假报成功 |
| 拒批后换键可重复申请相同变更 | 同参数、同资源版本的拒批持续生效 |
| 当前指标倒退时间戳冒充滞后历史 | 真实生成后延迟发布不可变样本，共享事故前历史 |
| 截断 JSON、异常路径泄漏 | 结构化裁剪并标记不完整，意外宿主错误不回显路径 |
| 超预算、API/审批异常丢失部分结果 | 保存已执行轨迹、用量和终止原因，超限响应不执行工具 |
| 并行工具批次绕过调用限制、状态正确掩盖中断 | 单独限制总调用；状态成功与正常完成分开判定 |
| 回放混入新试次、服务商缓存未隔离 | 正式入口默认禁用回放；统计排除回放；缓存绑定实际参数与地址 |
| 键冲突审计遗漏、特殊目录 URI 读取失败 | 键冲突持久记录；含 `#` 和中文目录的正常处置可正确判分 |

预算仍在服务商响应后估算，可能已经产生费用。轨迹与数据库事务分离，不承诺断电或跨系统原子性。测试证明的是上述反例在当前本地实现中的结果。

## 编号和文本捷径关闭了吗

三个共享告警模板与五类故障、三个参数种子全交叉，共 **45 个实例**；每个实例比较五种脚本，共 **225 条运行**。阻塞会话编号和等待者数变化，并加入无害会话 101。

| 策略 | 通过 |
|---|---|
| 根据业务状态调查后处置 | 45/45 |
| 旧编号查表 | 0/45 |
| 旧告警文本查表 | 0/45 |
| 固定确认误报 | 9/45 |
| 固定提高连接池上限 | 9/45 |

另将五个旧编号与五类故障全部交叉，放在隔离数据库中验证：状态扫描 **25/25**，编号查表 **4/25**。后者在对应编号与故障碰巧匹配时仍能成功，硬编码会话 101 在变动实例中失效。这个对照直接检验编号与状态脱钩，避免只用“新 UUID 不在旧字典里”证明修复。

这组实验关闭了所测的固定编号、固定文本和会话 101 路径；**没有证明全部捷径消失，也没有证明 LLM 泛化**。身份对照保留原有固定支付与连接池基线；新支付分支另改变目标、付款金额、行数和凭据。真实模型入口默认展开新决策分支，但尚未运行模型对照。详见 [反捷径结果](results/identity-results.json) 与 `test_audit.py` 的反例。

## 修复有效吗

原版能够通过冒烟测试，但下面这些反例暴露了执行和判分漏洞。修复后的结果来自当前复现脚本。

| 反例 | 修改前 | 修改后 |
|---|---|---|
| 未申请的可推导确认令牌 | 允许执行 | 无法授权 |
| 后端把合法支付金额改坏 | 判分仍通过 | 判分失败 |
| 换一个工具上下文后同键重试 | 重复执行一次 | 返回原结果，无重复副作用 |
| 终止不存在的会话失败后重试 | 假报成功 | 仍返回实际失败，键未被占用 |

新增测试还覆盖了**实际重建两遍、只记一次日志**的后端错误。判分器通过数据库变更量发现重复，无法仅靠一条正常日志蒙混过关。

进程恢复使用真实子进程中断测试，覆盖业务效果前、效果后提交前、提交后响应返回前三个位置：提交前全部回滚；提交后重试读取已存结果，审批只消费一次。此结果只验证本地 SQLite 进程恢复。

对照证据：[修改前结果](results/audit-results.json)、[修改后结果](results/audit-results-after.json)。审批测试由独立测试角色模拟决策；金额篡改是后端故障注入，不是模型拥有任意 SQL 写权限。

## 评测还存在哪些局限

不读监控的业务扫描规则，修改前后都能通过固定五场景：**5/5**。固定三种盲修的通过数从 **3/5** 降为 **1/5**，但这仍不足以证明 LLM 比规则强，或证明监控必不可少。

因此五场景用作功能回归，另设索引配对实验比较干预成本。两种实验分别报告，不拼成一个总体成功率。

## 配对实验说明了什么

每个配置有两个世界：初始业务状态相同，后台同步分别推进或停滞。重建在两个世界都安全。四个配置、八个世界成员，每种策略各运行八次；四种规则合计 32 条运行记录。

| 策略 | 正确且满足期限 | Agent 插入索引行数合计 | 完成 tick 合计 |
|---|---|---|---|
| 盲目重建 | 8/8 | 234 | 24 |
| 初始业务快照规则 | 8/8 | 234 | 32 |
| 等待后复查规则 | 8/8 | 117 | 44 |
| 监控规则 | 8/8 | 117 | 43 |

在这组实例上，等待后复查比盲目重建少插入 **50%** 的索引行，但完成时间从合计 24 tick 增至 44 tick。滞后监控的初始健康样本可能误导监控规则，因此它需预留兜底重建和最终核验时间。结果呈现的是**少干预与快完成的取舍**，没有单一策略全面胜出的结论。

旧版监控结果为 141 行、35 tick，使用的是“当前值配旧时间戳”的语义；本轮改为真实延迟发布后重新测量。两组观测协议不同，不能把数字变化当作同一条件下的性能提升。旧结果保留在 Git 历史和本地归档。

这里的行数只统计 Agent 触发的插入，后台自然补齐另计；tick 是仿真时间，不是真实延迟或经济损失。八个世界成员来自四个固定配置，不代表八个独立真实事故。完整轨迹见 [配对结果](results/pair-results.json)，配置和计量规则见 [设计说明](设计说明.md)。

## 结论的适用范围

本次环境为 Windows、Python 3.13.12、SQLite 3.50.4；完整依赖版本和采集时间见验证 JSON。

已经验证的是：合成故障可处置；本地授权与重试机制经反向测试；判分能发现所测的数据损害；规则策略存在时间与干预量的取舍。

仍缺少真实 LLM 对照及账单、真实 PostgreSQL 锁与回滚、其他 Python 版本和生产负载的证据。可信本地操作者可以访问原始文件；事务保证也不覆盖报告文件、外部 API、系统断电或跨系统操作。这些边界详见 [设计说明](设计说明.md)。
