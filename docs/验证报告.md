# 验证报告

目前验证了本地执行器和判分机制，**尚未验证真实 LLM 的处置能力**。32 项自动化测试、五场景正确脚本和四类规则实验均通过；全部使用合成 SQLite 数据，未调用模型 API。

## 修复有效吗

原版能够通过冒烟测试，但下面这些反例暴露了执行和判分漏洞。修复后的结果来自当前复现脚本。

| 反例 | 修改前 | 修改后 |
|---|---|---|
| 未申请的可推导确认令牌 | 允许执行 | 无法授权 |
| 后端把合法支付金额改坏 | 判分仍通过 | 判分失败 |
| 换一个工具上下文后同键重试 | 重复执行一次 | 返回原结果，无重复副作用 |
| 终止不存在的会话失败后重试 | 假报成功 | 仍返回实际失败，键未被占用 |

新增测试还覆盖了**实际重建两遍、只记一次日志**的后端错误。判分器通过数据库变更量发现重复，无法仅靠一条正常日志蒙混过关。

进程恢复使用真实子进程中断测试，覆盖业务效果前、效果后提交前、提交后响应返回前三个位置：提交前全部回滚；提交后重试读取已存结果，审批只消费一次。此结果只验证本地 SQLite 进程恢复。

对照证据：[修改前结果](results/audit-results.json)、[修改后结果](results/audit-results-after.json)。审批测试由独立测试角色模拟决策；金额篡改是后端故障注入，不是模型拥有任意 SQL 写权限。

## 评测还存在哪些局限

不读监控的业务扫描规则，修改前后都能通过固定五场景：**5/5**。固定三种盲修的通过数从 **3/5** 降为 **1/5**，但这仍不足以证明 LLM 比规则强，或证明监控必不可少。

因此五场景用作功能回归，另设索引配对实验比较干预成本。两种实验分别报告，不拼成一个总体成功率。

## 配对实验说明了什么

每个配置有两个世界：初始业务状态相同，后台同步分别推进或停滞。重建在两个世界都安全。四个配置、八个世界成员，每种策略各运行八次；四种规则合计 32 条运行记录。

| 策略 | 正确且满足期限 | Agent 插入索引行数合计 | 完成 tick 合计 |
|---|---|---|---|
| 盲目重建 | 8/8 | 234 | 24 |
| 初始业务快照规则 | 8/8 | 234 | 32 |
| 等待后复查规则 | 8/8 | 117 | 44 |
| 监控规则 | 8/8 | 141 | 35 |

在这组实例上，等待后复查比盲目重建少插入 **50%** 的索引行，但完成时间从合计 24 tick 增至 44 tick。监控规则在监控滞后时采用保守重建。结果呈现的是**少干预与快完成的取舍**，没有单一策略全面胜出的结论。

这里的行数只统计 Agent 触发的插入，后台自然补齐另计；tick 是仿真时间，不是真实延迟或经济损失。八个世界成员来自四个固定配置，不代表八个独立真实事故。完整轨迹见 [配对结果](results/pair-results.json)，配置和计量规则见 [设计说明](设计说明.md)。

在仓库根目录执行 `python -m scripts.validate`，全部检查通过时退出码为 0。

| 检查 | 当前结果 | 证据 |
|---|---|---|
| 授权、重试、崩溃、权限和判分反例 | 32 项自动化测试通过 | [测试输出与源码指纹](results/validation-results.json) |

修改前 JSON 随旧版本保存，当前验证命令不会覆盖它。其余 JSON 可由对应脚本重新生成。

## 结论的适用范围

本次环境为 Windows、Python 3.13.12、SQLite 3.50.4；完整依赖版本和采集时间见验证 JSON。

已经验证的是：合成故障可处置；本地授权与重试机制经反向测试；判分能发现所测的数据损害；规则策略存在时间与干预量的取舍。

仍缺少真实 LLM 对照及账单、真实 PostgreSQL 锁与回滚、其他 Python 版本和生产负载的证据。可信本地操作者可以访问原始文件；事务保证也不覆盖报告文件、外部 API、系统断电或跨系统操作。这些边界详见 [设计说明](设计说明.md)。
