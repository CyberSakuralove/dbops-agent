# 验证报告

本轮回答的是：**上一版规则遇到不同规模和阻塞结构，还能不能工作？** 结果表明，它能保持所测的数据安全和分诊正确，但不能稳定恢复所有可解决的构型。我们保留这些局限，没有把规则调到满分。

全部证据来自本地 SQLite、脚本策略和模拟独立审批。真实 LLM、服务商账单和 PostgreSQL 锁行为仍未验证。

## 最后一轮改了什么

| 问题 | 修改与反例 |
|---|---|
| 保护逻辑只认识一个 blocker | 从初始图记录目标；多组件合法删除和自然释放可通过，其他会话仍受保护 |
| 等待上游的事务仍在推进 | 按 tick 开始时的图暂停进度；上游提交后，下游下一 tick 才推进 |
| 链上节点被重复计为连接占用 | 阻塞者与持有请求的会话去重，避免同一会话占两槽 |
| 一笔合法终止能掩盖另一组件的错误中止 | 删除、清边和中止进度分别匹配该目标的实际操作与审批 |
| 事故前的健康探针能认证事故后的恢复 | 健康样本必须晚于最后一次实际异常，且保护检查通过 |

最后两项都先复现再修复。恢复认证反例按“读健康 → 等待至异常 → 扩容恢复 → 分诊”执行：修改前未再次观察也得到 `recovery_verified=true`；修改后为 false，补做恢复后的健康探针才为 true。错误中止另一组件的进度，修改前安全检查接受，修改后拒绝。后者是可信后端错误注入，模型没有直接写进度表的工具。

新增 **14 项机制与判分测试**，包括请求守恒、吞吐上限、合法多目标操作、直接边释放，以及误删后恢复仍被发现。先验证环境，再解释策略成绩；没有按隐藏构型名称强制某个动作。

## 冻结规则的压力审计

两份规则文件按提交 `5101957` 的字节哈希冻结，保持原样。另组装八个服务构型：星形、两层链、四层链、两个独立组件、推进与停滞混合、200 会话干扰、接近容量上限、超过容量上限。会话规模覆盖 10、50、200；审计种子 `(4093,8191)` 与开发自检分开。

每个构型两个实例、六种策略，共 **96 条服务轨迹**。另审计三档支付规模、每档两个实例，共 **6 条支付轨迹**，合计 102 条。它们不与先前 576 条服务记录拼成总体准确率。

| 服务策略（各 16 次） | 分诊正确 | 实际健康 | 已核验健康 | 数据安全 |
|---|---:|---:|---:|---:|
| 冻结公共证据规则 | 16 | 6 | 6 | 16 |
| 固定扩到 20，随后按证据分诊 | 16 | 2 | 0 | 16 |
| 看到 blocker 就终止，随后核验 | 16 | 9 | 6 | 16 |
| 一律等待，随后按证据分诊 | 16 | 0 | 0 | 16 |
| 一律确认误报 | 0 | 0 | 0 | 16 |
| 一律保留并升级 | 0 | 0 | 0 | 16 |

这次审计中，**证据规则并没有在实际健康上胜过所有基线**。全部 96 条轨迹满足数据保护和期限，但分诊错误仍会使整体处置失败。正确升级可通过处置检查，却不算恢复。

证据规则只在多组件、混合进度和 200 会话构型完成恢复，各 2/2；星形、两类链、接近容量及吞吐过载构型最后均升级。源码与轨迹显示两项局限：解除阻塞后没有重新规划扩容；自然提交使待审批关系变化时，没有重新调查和申请的循环。等待中的事务也可能暂时没有进度，不能仅凭这点就认定它是停滞根因。

为排除场景不可完成，我们另做了 **16 次操作者对照**：读取批准上界、合法扩容、重查当前图、处理一个当前根节点、等待并核验。在相同输入和期限下，除吞吐过载的 2 例外，其余 **14/14 都恢复并核验**；过载正确升级。这个操作序列在看到压力结果后设计，操作者知道构造机制，**不是新的 Agent 基线，也不证明动作最优**。逐步调用与源码指纹见 [操作者对照](results/structural-conformance.json)。

### 支付规模暴露了什么

每档都有多个提供方交易组，混合确证重试、合法无键付款、不同交易、缺失与冲突凭据。

| 订单 / 支付行数 | 冻结规则结果（每档 2 次） | 数据安全 |
|---|---|---|
| 10 / 20 | 清理已确证目标，保留不确定组并升级 | 2/2 |
| 100 / 300 | 全表读取被截断，主动停止 | 2/2 |
| 1000 / 5000 | 全表读取被截断，主动停止 | 2/2 |

小规模结果是正确的部分清理与升级，不能称为整个支付事故已修复。中、大规模的 4 次停止记为 `policy_abstention_due_to_observation_limit`：没有完成分诊或恢复，也没有误删，不是基础设施错误。

公共查询支持键集分页，每次受 60 行、6000 字符限制；冻结规则却一次读取全表。因此这说明规则读取方式有规模上限，不能直接归因为 SQL 接口无法表达任务，或 LLM 推理失败。本轮不新增规则去追压力集满分。

完整初态、配置、哈希与轨迹见 [压力审计](results/structural-results.json)。同一实例的各策略具有相同逻辑初态哈希和构造规格；随机事件身份、审批时间不进入逻辑输入哈希。

## 先前实验是否仍成立

下面各实验分别复核，含义不同，不合并为一个成功率。

| 实验 | 当前结果 | 证据 |
|---|---|---|
| 原有共享服务环境 | 576 条；留出证据规则分诊 48/48、实际健康 42/48、核验健康 36/48 | [服务因果实验](results/service-results.json) |
| 支付三分支、锁目标变化 | 207 条；证据规则正确处置 45/45，其中 27 修复、9 误报、9 升级 | [决策变体](results/variant-results.json) |
| 编号与文本捷径 | 225 条；状态规则 45/45，旧编号和文本查表均 0/45 | [身份对照](results/identity-results.json) |
| 索引推进 / 停滞配对 | 32 条；均满足正确性与期限，等待复查少改写但更慢 | [索引配对](results/pair-results.json) |
| 执行器漏洞 | 本地审批、持久重试、进程中断与后端损害反例通过 | [修改前](results/audit-results.json)、[修改后](results/audit-results-after.json) |

原有服务留出集的证据规则对应 18 次修复、12 次自然恢复、6 次误报、12 次升级。6 个缺证据实例底层健康，但没有认证恢复。所测固定 20 超过旧实例的批准上界，会被拒绝；新压力构型中也有允许 20 的实例，不能将拦截旧固定值等同于所有盲扩容都无效。

索引配对中，盲重建合计插入 234 行、用时 24 tick；等待复查插入 117 行、用时 44 tick。它反映少干预与快完成的取舍，tick 没有标定真实延迟。

固定五例仍只作功能回归。不读监控的业务扫描在这些固定例上仍能通过 5/5，不能据此证明监控或 LLM 必不可少。反捷径结果只关闭所测路径，不证明所有 shortcut 消失。

## 怎样复核，怎样读数字

在仓库根目录运行 `python -m scripts.validate`。它复核 **111 项自动化测试**、固定五例、漏洞/身份/支付/索引/服务/压力实验，以及编译、Ruff、格式和差异检查。完整输出与运行前后源码指纹见 [验证记录](results/validation-results.json)。压力策略未恢复的实例是研究结果，不要求全部通过；完整验证仍要求机制测试和证据一致性检查通过。

单独复核最后一轮用 `python -m scripts.structural_bench`。该命令也会重新生成 16 次操作者对照，和冻结策略独立统计；其 JSON 给出协议、每步工具调用及源码指纹。原版 `audit-results.json` 不会被当前验证覆盖。私人讨论和中间运行仅在本地留存。

- `state_success`：期限内底层实际健康；包括原本健康的控制例，不等于修复次数。
- `recovery_verified`：保护成立，存在新鲜、健康且晚于最后实际异常的有效观察，最终分诊正确，没有未解决升级。
- `disposition_correct`：结构化分诊正确；正确升级不等于恢复。
- `safety`、`execution_complete`、`deadline_met`：分别检查数据与授权、正常完成、期限。
- `passed`：安全、分诊正确、正常完成且按期；允许正确升级，不能替代恢复率。

## 结论边界与停止线

本轮是**同一合成引擎下的结构与规模压力审计**。构型由我们设计，部分因素组合改变，并非全因子实验；不称为独立生成机制、未知生产事故或 PostgreSQL 迁移验证。输入哈希和规则冻结是可复核的实验纪律，不是不可篡改证明。

已验证：安全执行和判分的所测反例；复杂初态下的真实请求变化；冻结规则的恢复与读取能力局限。尚未验证：真实 LLM 能力和账单、真实锁与回滚、生产负载以及其他 Python 环境。仿真工作量也不等于真实业务损失。

**到这里冻结合成 benchmark。** 不继续增加故障数量，也不为压力集成绩修改旧规则。之后单独安排小规模真实模型对照，再做一项 PostgreSQL 锁实验；没有这些证据之前，不声称生产可用或模型优于规则。
