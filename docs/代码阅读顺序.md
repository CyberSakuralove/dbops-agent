# 代码阅读顺序

先跟踪一次支付去重，再读模型循环和配对实验。下面按理解主线排列，不需要一开始遍历所有文件；目录职责见 [项目结构](项目结构.md)。

## 先运行一次

在仓库根目录执行 `python -m scripts.smoke`，再跟着 [独立审批演示](../README.md#独立审批演示) 观察申请、批准、执行和同键重试。两项都不调用模型 API。演示已有目录时使用新的 `--dir`，每条命令保持同一个目录。

## 1. 找到入口和场景

读 [scripts/demo.py](../scripts/demo.py) 的 `main`，跟踪 `init`、`request`、`execute`、`judge` 四个分支。接着看 [scenario.py](../dbops_agent/tasks/scenario.py) 的 `Scenario`、`load_scenarios` 和 [seed.yaml](../dbops_agent/tasks/seed.yaml)。

目标：分清给模型的告警、评测侧根因和成功性质。

## 2. 看故障怎样产生

读 [schema.py](../dbops_agent/incident/schema.py) 的业务初态，再读 [faults.py](../dbops_agent/incident/faults.py) 的 `build_fixture`、`DuplicateWrite.inject` 和 `properties`。留意注入方法包装后会调用 `protection.arm`。

目标：找到合法支付和无键副本，解释为何业务数据与监控可能不一致。其他四类故障可以随后对照阅读。

随后读 [variants.py](../dbops_agent/incident/variants.py) 的 `_payments` 和 `_sessions`：比较同一账本外观下的三种凭据，找出为什么应分别修复、升级或确认误报。锁变体则观察 active/idle 阻塞者与无害长事务的区别。

接着读 [identity.py](../dbops_agent/incident/identity.py) 与 [cases.py](../dbops_agent/incident/cases.py)，分清内部故障标签、持久事件身份和告警模板。用 [test_audit.py](../tests/test_audit.py) 的编号置换测试理解“随机编号仍不足以证明诊断能力”。

## 3. 跟踪工具调用

按 [base.py](../dbops_agent/tools/base.py) → [registry.py](../dbops_agent/tools/registry.py) → [library.py](../dbops_agent/tools/library.py) 阅读。重点是参数校验、`ToolRegistry.call`、`QueryBusinessDb.run` 和 `DeduplicatePayments.apply`。

目标：解释 JSON 怎样成为参数对象、只读权限在哪里实施、去重 SQL 删除什么。注意写动作使用执行器的连接，不自行提交。

支付去重的公开契约在 [payment.py](../dbops_agent/incident/payment.py)。重点看必填 `payment_ids`、完整交易组重验、最小 ID 保留行，以及为何 NULL 键本身不能证明重复。`EscalateIncident` 只记录未解决事项，不能代替修复。

## 4. 深读审批和重试

先看 [policy.py](../dbops_agent/guard/policy.py) 的动作分级和参数限制，再看 [execution.py](../dbops_agent/guard/execution.py) 的 `execute`、`ApprovalService.decide`、`fingerprint`、`resource_version`。

执行顺序是：查已有结果 → 检查权限与审批 → 执行业务效果 → 同一事务保存结果、消费审批并提交。**完成结果查询在已消费审批校验之前**，所以提交后响应丢失仍能恢复原结果。

对照 [test_safety.py](../tests/test_safety.py) 的持久重试、部分写失败、并发和真实进程中断测试。目标：讲清申请 ID 为什么不能授权自己，以及失败、重启和并发时是否再次施加变更。

## 5. 追到判分

按 [assertions.py](../dbops_agent/contract/assertions.py) → [protection.py](../dbops_agent/judge/protection.py) → [outcome.py](../dbops_agent/judge/outcome.py) 阅读。重点是 `Assertion.check`、`arm`、`check`、`unrecorded_rebuilds` 和 `judge`。

对照 `test_double_rebuild_with_single_executor_log_is_detected` 与金额篡改测试。目标：解释为什么工具成功、行数正常、日志只有一条，仍可能判失败；分清最终字段损害和已提交的越界过程。

再看 [test_variants.py](../tests/test_variants.py) 的旧 NULL 后端、凭据变动和误删后恢复测试。运行 `python -m scripts.variant_bench`，跟踪 [evidence_policy.py](../scripts/evidence_policy.py) 的公共证据规则；它不调用工具的重复判定函数，也不读取评测文件。对照结果中的 repaired 与 unresolved_escalated，练习解释“正确升级为什么不算修复”。

## 6. 理解模型循环

先读 [trace.py](../dbops_agent/record/trace.py) 的 `Step`、`Trace`，再读 [bare_loop.py](../dbops_agent/runtimes/bare_loop.py) 的 `run` 和 `_complete`。用 [test_runtime.py](../tests/test_runtime.py) 核对未审批暂停、多个工具调用的 token 统计和回放。

目标：讲清模型如何根据反馈选择下一步，独立审批回调在哪里，何时停止。首次阅读只看源码，不运行付费入口。

再看 `test_audit.py` 的预算、API、审批异常和批量工具调用测试，确认中断前哪些效果已发生、哪些提议没有执行。

## 7. 理解配对和成本

读 [index_pair.py](../dbops_agent/incident/index_pair.py) 的 `PairEnvironment`、`PairRegistry.call`、`baseline`、`outcome`，配合 [pair_bench.py](../scripts/pair_bench.py) 与 [test_pair.py](../tests/test_pair.py)。

运行免费的 `python -m scripts.pair_bench`，在 [配对轨迹](results/pair-results.json) 中比较同一配置的两个世界。先跟 `wait_recheck_rule`，再对比盲修和监控规则。

目标：分清 Agent 改写与后台自然插入，并解释为何安全盲修都能通过，却需要比较时间和干预量。

接着读 [service.py](../dbops_agent/incident/service.py) 的 `advance`：先跟踪请求获得连接、等待 blocker、完成及归还连接，再比较扩容和终止怎样改变同一条路径。读 [service_tools.py](../dbops_agent/incident/service_tools.py) 的容量检查和终止前重验，最后看 `outcome` 怎样将实际健康、已验证恢复和正确升级分开。

运行免费的 `python -m scripts.service_bench`，再读 [service_policy.py](../scripts/service_policy.py)。重点比较证据规则与“看到 blocker 就终止”：正常事务中两者可以都安全正确，但中止工作量不同。用 [test_service.py](../tests/test_service.py) 的相同初态、不同后续进度和旧审批反例复核；分清校准种子与冻结留出，不能把新种子称为新真实事故。

## 8. 看规则会在哪些新结构下失效

先读 [diversity.py](../dbops_agent/incident/diversity.py) 的 `SERVICE_CONFIGS`、`compose_service` 和 `build_payments`，看星形、链式、多组件以及不同负载怎样变成实际初态。再读 [structural_bench.py](../scripts/structural_bench.py)：它调用上一版的规则，不按新结果改规则；哈希绑定旧提交中的两个策略文件。

跟踪 [test_diversity.py](../tests/test_diversity.py) 的合法终止、清除直接边和无关会话误删反例，解释判分器如何接受多组件自然释放，同时拒绝借用另一目标的审批记录。最后运行免费的 `python -m scripts.structural_bench`，结合 [验证报告](验证报告.md) 阅读未通过和主动中止的实例。

目标：区分模拟器错误、策略能力边界与真实数据库迁移。扩大数据库不能自动证明泛化；先前的满分也不能替代这次审计结果。

## 9. 跟踪 V2 怎样补通用能力

先读 [access.py](../dbops_agent/policies/access.py)：它只通过工具获得证据，逐次计入调用和公开时钟，预留分诊余量，审批仍交给外部角色。接着读 [service_v2.py](../dbops_agent/policies/service_v2.py) 的 `stalled` 和 `run`，跟踪“当前根节点 → 两次进度 → 一个动作 → 新观察”。注意等待中的下游事务不能因进度暂停而被当作停滞根因。

再读 [payment_v2.py](../dbops_agent/policies/payment_v2.py) 的 `SUMMARY`、`page`、`group_targets`：聚合只提供公开事实，拟删除组仍要读完整凭据；页数、行数或预算不完整就保留并升级。5000 行仍可能只安全处理部分目标，不能跳过完整性检查。

最后读 [context.py](../dbops_agent/runtimes/context.py)：它保留最新两次图/进度、最新探针和容量计划；旧异常证据、SQL、写操作及失败保留，未解决审批期间不裁剪。结合 [test_policy_v2.py](../tests/test_policy_v2.py) 验证审批状态变化和裁剪不改原始轨迹。运行 `python -m scripts.validate_v2`；其对照是已知回归，不是新泛化测试。

## 10. 补齐缓存、费用和报告

最后读 [cassette.py](../dbops_agent/record/cassette.py)、[ledger.py](../dbops_agent/record/ledger.py)、[config.py](../dbops_agent/config.py)，再看 [report.py](../dbops_agent/judge/report.py) 与 [pilot.py](../scripts/pilot.py)。

目标：分清本地回放与新模型试次、token 用量与估计费用、单次结果与多次统计。真实模型的当前状态见 [验证报告](验证报告.md)。

## 面试前检查

尝试脱离源码讲清：支付去重的完整路径；丢失响应后的重试；相同告警为什么可能扩容、解除阻塞或升级；等待与提前终止的成本差异；冻结规则为什么还会在大规模查询中主动停止。再指出源码和反例，避免只记住数字。
