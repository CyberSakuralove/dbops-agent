# 代码阅读顺序

建议沿着“一个故障如何构造、工具如何处置、结果如何被验证”的主线阅读。先掌握支付去重案例，再扩展到模型循环和索引配对实验。目录全貌见 [项目结构](项目结构.md)，实现边界见 [修复实施说明](修复实施说明.md)。

## 读之前先看见一次运行

在仓库根目录执行免费的 `python -m scripts.smoke`，观察五个正确脚本的结果和反向测试。然后按 [README 中的独立审批演示](../README.md#独立审批演示) 走一次申请、独立决策、执行和同键重试。

演示目录已存在时，用新的 `--dir`；每条演示命令都使用同一个目录。`approve.py` 接收该目录里的 `business.db`。阅读代码不需要调用模型 API，下面涉及 `pilot.py` 和 `--llm` 的阶段先只读源码。

## 第 7 步：最值得画出来的执行顺序

按照 `execute` 的代码顺序，自己画一次 L1 操作：

1. 开始 `BEGIN IMMEDIATE`，初始化执行元数据，并查询是否已有完成结果。
2. 同事故、同键、同动作和参数已完成时，直接返回持久结果；同键冲突拒绝。
3. 没有完成记录时，检查静态权限。L1 没有申请 ID 时保存申请，只返回 ID。
4. 独立操作者决策后，重试核验事故、键、参数指纹、资源版本、有效期与批准状态。
5. 调用动作的 `apply`；失败回滚，不消费审批、不写成功结果。
6. 成功时在同一个事务保存操作结果、消费审批、写审计并提交。

这段代码的关键顺序是：**完成结果查询在已消费审批校验之前。** 因此首次执行提交成功但响应丢失时，同一逻辑操作仍能恢复原结果。还要分清“再次返回原结果”和“重新施加一次变更”。

对照 `test_persistent_retry_returns_original_and_consumes_once`、`test_partial_failure_rolls_back_effect_and_approval`、`test_concurrent_contexts_apply_once` 和 `test_real_process_crashes_at_transaction_boundaries` 阅读。再看资源变化后恢复原值的测试，理解版本号为何不能只靠最终内容摘要代替。

## 第 9 步：不要只盯着成功返回值

按以下顺序检查一个坏后端：动作返回成功 → 审计只有一条 → 最终行数正确 → 判分仍然失败。去看 `test_double_rebuild_with_single_executor_log_is_detected`，找出变更见证和 `unrecorded_rebuilds` 如何交叉验证实际插入量。

再看合法支付金额篡改和“改坏后恢复”两项测试。前态字段比较负责发现最终损害，变更见证负责发现允许变更范围之外的已提交过程。二者各自能发现什么、不能发现什么，都要能说清楚。

## 第 11 步：先运行规则，再读模型入口

运行 `python -m scripts.pair_bench`，然后查看 [pair-results.json](pair-results.json) 中一个配置的推进、停滞两成员。

先跟踪 `wait_recheck_rule`：读取覆盖 → 等待 → 再读覆盖 → 判断是否推进 → 继续等待或重建。再与 `blind_rebuild` 和 `metrics_rule` 比较。注意 Agent 改写、后台自然插入、诊断调用和完成 tick 是分开统计的。

最后查看同工具权限的 LLM 入口。本地规则结果不证明模型更强；当前真实模型对照仍待测。能解释这个限制，也是理解评测设计的一部分。

## 面试前的复述检查

读完后，尝试不用源码回答这五个问题，再用代码定位证据：

- 一次支付去重从告警到判分经过哪些层？哪些信息对模型可见？
- Agent 为什么拿到申请 ID 仍不能批准自己？可信本地操作者的权限是什么？
- 同键重试如何应对进程中断、并发、失败和提交后响应丢失？
- 为什么“工具成功、行数正常、日志正常”仍不足以证明正确处置？
- 配对实验里调查与干预的收益和代价分别如何计量？目前结果支持哪些结论？

如果只准备第一轮讲解，优先读完第 1～10 步，把支付去重、一个判分反例和模型如何调用工具讲清楚；后续再扩展到第 11～12 步的成本评测与记录。
